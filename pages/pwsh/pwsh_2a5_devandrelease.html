モジュールを含むスクリプトの開発と配布

何が問題ですか？

１つのスクリプトファイルだけであれば、開発も1つのファイルで配布も１つのファイルなので問題は無いです（ps1スクリプトを実行できない人向けにバッチファイルも作るので実際は複数ファイルだけど）

しかし、ps1ファイル内でモジュールの関数を使っている場合は、そのモジュールファイルを含めて配布しないといけないです（当然）

例えば、自分で開発して自分だけが使う場合、PSModulePathに自作モジュールを置いて置けばいいですが、配布する場合PSModulePathにモジュールを置いているとユーザ先にもそのパスにモジュールを置きなおしてもらう必要（またはインストーラを作りモジュールをPSModulePathに配置するなどが必要）があります。

PSModulePathを使うメリットとデメリット

自分の場合、配布を考えるとこのデメリットがあるため「PSModulePath」を使わないという結論になりました

  • メリット

    開発時はImportのパスを指定しなくていいので楽

  • デメリット

    main.ps1スクリプトが、PSModulePathを参照しているので、配布先でもこのパスにモジュールを配置してもらわないといけない。

対応方法（開発側）

配布を考えた場合、PSModulePathを使うのはあまり良くないという結果になったので他の方法を検討してみた結果、$PSScriptRoot という自動変数でps1スクリプトから相対パス指定したら良さそうというのが分かりました


          #開発環境イメージ
          C:\MyCmd
            ├ myScriptFiles
            │   ├ main.ps1                      ← myModuleA、myModuleBをインポートする親スクリプト
            │   ├ 他のps1（配布とは関係ない）
            │   ├ 他のps1（配布とは関係ない）
            │   └ ・・・
            ├ myModules
            │   ├ myModuleA
            │   │  ├ myModuleA.psm1
            │   │  └ myModuleA.psd1
            │   └ myModuleB
            │       ├ myModuleB.psm1
            │       └ myModuleB.psd1

PSModulePathを使わないパス指定

  • $PSScriptRootを使った変数を作るやり方（没）

    上記の開発環境のイメージだと「main.ps1」の1つ上のフォルダに上がり、そこから見える「myModules」パスにmyModuleA、myModuleBがおるのでこのパスを指定したらいいです

    この方法はいいのですが、モジュールが増える度に「$thisModulePathB」「$thisModulePathB」・・・と変数が増えていくので、今後拡張等を考えるとあんまり良くない。このためこの案は没 

    
              #main.ps1に追加するコード
              $thisModulePath = Join-Path $PSScriptRoot "..\myModules\myModuleA\myModuleA.psd1"
              Import-Module $thisModulePath
  • モジュールルートだけ変数化して、この変数と$PSScriptRootで相対パス指定する

    この方法は、モジュールの置き場が変更になってもモジュールルート変数だけ変更すればいいので保守性も高いと思います

    
              #main.ps1に追加するコード
              $thisModuleRoot = Join-Path (Split-Path $PSScriptRoot -Parent) "myModules"
              Import-Module (Join-Path $thisModuleRoot "myModuleA\myModuleA.psd1")
              Import-Module (Join-Path $thisModuleRoot "myModuleB\myModuleB.psd1")
              ・・・

対応方法（配布側）

配布側は特に気を付ける点は無いかと思います

main.ps1は、開発時から$PSScriptRootから相対パスでモジュールをインポートしているので、このフォルダ構造のままリリースすれば、コード修正も不要だしユーザ環境を加工する必要もないです

ユーザがzipを展開した先が実行環境となり、モジュールもその$PSScriptRootから相対パス指定されるので問題ないです


          #リリースイメージ
          リリース機能名.zip        ← zipで全体を圧縮
            ├ リリース機能名       ← 開発時のmyScriptsFolder
            │   └ main.ps1        ← $thisModuleRoot = Join-Path (Split-Path $PSScriptRoot -Parent) "myModules"
            │                         Import-Module (Join-Path $thisModuleRoot "myModuleA\myModuleA.psd1")
            ├ myModules
            │   ├ myModuleA
            │   │  ├ myModuleA.psm1
            │   │  └ myModuleA.psd1
            │   └ myModuleB
            │       ├ myModuleB.psm1
            │       └ myModuleB.psd1

Split-Path の誤解（参考）

上記に「Split-Path $PSScriptRoot -Parent」というコードがありますが、誤解していたのでメモ書きしておきます


          # Split-Path の誤解
          $PSScriptRootは、今実行したps1スクリプトファイルのパスが格納される
          例）C:\MyCmd\Pwsh\TESTCODE\hoge.ps1
          この時、$PSScriptRootには C:\MyCmd\Pwsh\TESTCODE が代入されます

          次に、Split-Path $PSScriptRoot -Parent を実行すると
          「C:\MyCmd\Pwsh」が返ってきます。
          Split-Path -Parentは、最後の要素（例だとTESTCODE）を除く親パスを返すからです
