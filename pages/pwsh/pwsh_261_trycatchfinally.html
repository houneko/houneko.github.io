PowerShellのtry～catch～finallyによる例外処理

try～catch～finally

try～catch～finallyは、プログラム実行中に発生する例外に対するエラーハンドリングの構造を記述するもの。try～catch～finallyは複数書くこともできるしネストすることもできる

try～catch～finallyの基本的な構造


        #try～catch～finallyの構造
        try{
          #ここに例外が発生する可能性がある処理を書く
          ...
        }
        catch {
          #ここはtryで発生した例外に対する処理を書く
          ...
        }
        finally {
          #finallyブロックは例外が発生した場合も発生しなかった場合も実行される
        }
  • tryブロック

    tryブロックは、例外が発生する可能性がある処理を記述する。例外が発生した場合、catchブロックに捕獲される

  • catchブロック

    catchブロックは、tryブロックで発生した例外がキャッチされる部分

    無印のcatchは、catch [System.Exception] の省略形となっている。つまり、catchの後に例外の型を指定することで、それぞれの例外に対する処理を分けて書くことができる。その場合、上から順に評価され該当するcatchだけが実行される

    • 例外型毎のcatchブロック

      例外型に応じたcatchブロックを作ることで、その例外に適したエラーハンドリングができる。ただし全部の例外型のcatch文を書くのは現実的ではないので、想定する型だけ書けばいい。

      しかし、いろいろ調べてみると例外型は多数あり、.NETの例外型もあるので一旦全てのケースとして「無印のcatch」で確実にキャッチしてからそのブロック内で例外型を調べて発生した例外型にあう処理を書いた方がいいかもしれない。今後の研究ネタかな 

      
                try {
                  Get-Content "hoge.txt" -ErrorAction Stop
                }
                catch [System.UnauthorizedAccessException] {
                  #この例では、ここには入らない
                  Write-Host "例外：アクセス権がない"
                }
                catch [System.IO.FileNotFoundException] {
                  #この例では、ここには入らない
                  #ファイルが存在しないという例外は一緒だが、この例外型は.NETの例外型のため
                  Write-Host "例外：ファイルが見つからない（.NET）"
                }
                catch [System.Management.Automation.ItemNotFoundException] {
                  #この例では、ここには入る
                  #これはファイルが存在しないという例外のPowershellの例外型だから
                  Write-Host "例外：ファイルが見つからない（PowerShell）"
                }
                catch {
                  #全ての例外はここに入るが、これよりも前に該当する例外catchがあれば、ここには入らない
                  Write-Host "例外：その他のエラー"
                }
  • finallyブロック

    finallyブロックは、例外が発生した場合もしなかった場合も基本的に必ず 入る。これがfinallyブロックの存在意義かと思います

    finallyブロックにはオープンしてたものをクローズするとか、設定した値を元に戻すとか、ロックを解除するとかの処理だけを書くようにする。ここに制御構造を入れたらバグが入る可能性があるしデバッグが難しくなる可能性がある。なので、状態復帰関係の処理だけ書くようにする

    特にreturnは書いたらだめ（PowerShellでは書けないようになっている）。また、後始末用の関数を作っておき、finallyブロックからそれをコールしてもいいが、この場合後始末用の関数はthrowを投げないようしないといけない

    • finallyブロックの必要性

      finallyブロックは場合によっては必要ないけど、場合によっては必要。どういう時に必要かと言うと、try/catchの中から抜けてしまう可能性がある場合、finallyブロックを作って確実に後始末ができるようにする

      以下のサンプルは、try～catchで例外が発生しようがしまいが処理Zに行くから、finallyブロックの存在意義は無いんじゃないと思ったケースです。一見、処理Zは例外有無によらず実行されるように見えるけど、実行されないケースも起こりうる。そうすると処理Zで予定していたクローズ処理などの後始末ができずに終わってしまう可能性がある 

      
                try {
                  # 例外が発生する可能性がある処理
                  ...
                }
                catch {
                  # 例外が発生した場合の処理
                  ...
                }

                # 処理Z             # finallyブロックが無くても、例外有無によらず
                ...                 # この処理Zは実行されるはずでは？ じゃ、finallyブロックの存在意義は？

      以下のコードは、catchブロックでreturn がある。また、finallyブロックが無いのでここでリターンしてしまう

      このため、後始末処理であるクローズやリセット処理が実行されなくなる

      
                try {
                  # 例外が発生する処理
                  Get-Content "throw.txt" -ErrorAction Stop
                }
                catch {
                  Write-Host "例外： $($_.Exception.GetType().FullName)"
                  return "AB"
                }
                # finallyブロックを使わずにファイルクローズなどの後始末をする
                My-CloseHoge                                              # ← catchブロックでreturnしているので、
                My-ResetHoge                                              # ← この処理は実行されなくなる。〃
                Write-Host ("end test")                

                ### 実行結果 ###
                PS> myErrorTest.ps1
                例外： System.Management.Automation.ItemNotFoundException   ← 発生した例外型
                AB                                                          ← catchブロックでreturnしたコード

      じゃ、このコードにfinallyブロックを入れるとどうなる。catchブロックでreturnがあるのにfinallyブロックに入るのか？

      catchブロックにreturnがあっても、finallyブロックには入れる。このため、finallyブロックでクローズなどの処理を実行することが可能

      
                try {
                  # 例外が発生する処理
                  Get-Content "throw.txt" -ErrorAction Stop
                }
                catch {
                  Write-Host "例外： $($_.Exception.GetType().FullName)"
                  return "AB"                                               # ←catchブロックでreturnしているが
                }
                # finallyブロックでファイルクローズなどの後始末をする
                finally {
                  Write-Host ("this is finally block.")                     # ← finallyブロックには入る
                  My-CloseHoge
                  My-ResetHoge
                }
                Write-Host ("end test")                                     # ←??

                ### 実行結果 ###
                PS> myErrorTest.ps1
                例外： System.Management.Automation.ItemNotFoundException   ← 発生した例外型
                AB                                                          ← catchブロックでreturnしたコード
                this is finally block.                                      ← finallyブロックに入っている
                start My-CloseHoge
                start My-ResetHoge

      つまり、catchブロックでreturnしていていも、finallyブロックは実行される。

      しかし、finallyブロックの後にある「Write-Host ("end test")」は実行されていない。なんでか？？

      この例では、catchブロックでreturnしている。しかし、finallyブロックがあるので、finallyブロックには入り処理が行われる。その後、finallyブロックの処理が終れば、returnが実行されるから

      じゃ、catchブロックのreturnを外したら、finallyブロックの後の「Write-Host ("end test")」は実行されるの？答えはYES

      returnが削除されたらfinallyブロック実行後に「Write-Host ("end test")」が実行される

    • じゃ、finallyブロックでreturnしたらいいのでは？

      PowerShellでは、finallyブロックにはreturn制御コードは書けないようになっている。

      ただし、書けたとしてもfinallyブロックにはreturnは書いたらだめ。これはfinallyブロックのreturnにより例外のエラー情報はかき消されるため
