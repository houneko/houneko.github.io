PowerShellの環境変数

PowerShellの環境設定変数

この変数もPowerShellが自分せ設定するので自動変数の一種だけど、環境設定変数はユーザが設定を変えることができる

詳しくは、Microsoftの「about_Preference_Variables」ページで

自分が良く使う環境設定変数

  • 「$ConfirmPreference」は、確認画面を出すか出さないかのボーダー値である

    $ConfirmPreference環境設定変数は、PowerShellのコマンドレットや関数が重要な変更を加える可能性があると判断した場合に「この操作を実行しますか？ はい（Y） いいえ（N）・・・」のようなメッセージを出すかどうかを制御する設定変数

    $ConfirmPreferenceの主な設定値
    設定値 値の意味
    None 確認表示を完全に出さない
    Low ConfirmImpactがLow以上の動作の場合、確認が出る
    Medium ConfirmImpactがMedium以上の動作の場合、確認が出る
    High（デフォルト） ConfirmImpactがHigh以上の動作の場合、確認が出る
    Internal 内部用。通常は使用しない

    $ConfirmPreference環境設定変数は「確認画面」を出すか出さないかを制御するものというのは、わかった。じゃ、どういう場合だとこの確認画面が出るのか？という疑問が出てくると思います。結論は以下

    確認が発生するのは、実行するコマンドレットの「ConfirmImpact」の値が、$ConfirmPreference値以上の場合である。

    どういうことかと言うと、今から実行する処理のインパクトレベルがボーダー値（$ConfirmPreferenceの値）以上となっている場合、その処理を実行すると何かまずいかもしれんということで、ユーザに確認が発生する

    テストしてみる

    1. テストとして「Remove-Item」を実行する、Test.ps1スクリプトを作成
    2. Remove-Itemの ConfirmImpactを調べる 
      
              PS> $cmd = Get-Command Remove-Item
              PS> $attr = $cmd.ImplementingType.GetCustomAttributes($true) | Where-Object {$_ -is [System.Management.Automation.CmdletAttribute]}
              PS> $attr.ConfirmImpact
              Medium  # ← Remove-Item の ConfirmImpactは「Medium」であることが分かる
    3. $ConfirmPreferenceの値を下げる（確認が出やすいようボーダー値を下げる） 
      
              PS> $ConfirmPreference = 'Low'
              PS> $ConfirmPreference
              Low  # ← $ConfirmPreferenceの値が Low に変わった事が確認できる
    4. Test.ps1スクリプトを実行して、確認画面が出るかテストしてみる 
      
              PS> ./Test.ps1   #Remove-Item を含むスクリプトを実行してみる

              # ↓ Remove-ItemのConfirmImpactは「Medium」に対して、$ConfirmPreferenceの値は「Low」なので 確認画面が表示された。
              Confirm
              Are you sure you want to perform this action?
              Performing the operation "Remove File" on target "C:\Users\houneko\OneDrive\My\TEST_CODE_用\PowerShell関係\hoge.bat".
              [Y] Yes  [A] Yes to All  [N] No  [L] No to All  [S] Suspend  [?] Help (default is "Y"):
  • 「$DebugPreference」は、Write-Debug コマンドレットの挙動を制御するための設定値である

    $Debugpreferenceは、タイトルの通りWrite-Debugコマンドレットが実行される時に「表示するのか」「確認を求めてから表示するのか」「何もしないのか」などの挙動を変えるための設定値である

    $DebugPreferenceの主な設定値
    設定値 値の意味
    SilentlyContinue (デフォルト) デバッグメッセージを表示しない
    Continue デバッグメッセージを表示し、スクリプト実行を続行
    Inquire デバッグメッセージを表示し、続行するか確認を求める
    Stop デバッグメッセージを表示し、エラーとして停止

    テストしてみる

    この例は、[CmdletBinding()]で高度化しているので、コマンドラインから「-Debug」をつけるだけで$Debugpreferenceの値が変わり、Write-Debugが表示されるようになっている 

    
            [CmdletBinding()] 
            param()

            write-host("This is Test.ps1")
            Write-Host($DebugPreference)
            Write-Debug("Enter")
            Write-Debug("Exit")

            # ================
            # 実行結果１
            > .\Test.ps1   # ← そのままTest.ps1スクリプトを実行してみる
            This is Test.ps1
            SilentlyContinue  # ← $Debugpreferenceの値はデフォルト値（なので、Write-Debugは表示されていない）

            # ================
            # 実行結果２
            > .\Test.ps1 -Debug  # ← -Debugオプションをつけて、Test.ps1スクリプトを実行してみる
            This is Test.ps1
            Continue                # ← $Debugpreferenceの値が変更されている。
                                    #    これは[CmdletBinding()]を設定しているから、高度化されているため
            DEBUG: Enter            # ← Write-Debugの結果が表示されている
            DEBUG: Exit

    Windows PowerShellにおける$DebugPreferenceとWrite-Debug問題

    これは現場で起きた事象です。部内向けのスクリプト（snowflakeのコマンド入力を代行するスクリプト）を作った時、Write-Debugで実行の確認「この操作を実行しますか？」が出るようになりました。PowerShell Core環境だと確認がでないのでますます混乱。。

    まず調べた事は「$ConfirmPreference = 'none'」かですが、これは正しく設定している（$ConfirmPreferenceがnoneでも各コマンドレットの処理に「-Confirm」スイッチがついてると確認が出るがこれも指定はしていない）。

    次に調べたことは、Windows PowerShellとPowerShell Coreでのこの変数の違いです

    部内ではPowerShell Coreを使っている人はいない（事務職なので当たり前）ので、スクリプトの実行環境はWindows PowerShellになります。ここが、問題の起点でした。

    Windows PowerShellとPowerShell Coreでの比較結果
    Windows PowerShell環境 PowerShell Core環境
    スクリプト内での$Debugpreferenceの値 Inquire Continue
    シェル上での$Debugpreferenceの値 SilentlyContinue SilentlyContinue
    確認メッセージの有無 出る 出ない

    なんでこの差がでたのか？

    実は、$Debugpreferenceの値はスクリプト上で設定していない。なのになんでこのような差がでてしまうのか？。これはWindows PowershellとPowerShell Coreのデバッグに対する設計思想の違いになる。Windows Powershellのデバッグ設計は「対話重視」なので、$DebugPreferenceのデフォルト値は「Inuquire」になりやすいが、PowerShell Coreのデバッグ設計は「自動化重視」なので$DebugPreferenceのデフォルト値は「Continue」になる

    シェルとスクリプトで$DebugPreferenceの値が違うのはシェルとスクリプトではスコープが違うから

    何がトリガだったのか？

    このスクリプトは関数の高度化を指定しています。つまり[CmdletBinding()]属性を付けている。これがトリガであった。
    [CmdletBinding()]により「-Debug」オプションが使えるようになりますが、この時Windows PowershellとPowerShell Coreの違いにより$DebugPreferenceの値が異なっており、Windows Powershellでは確認メッセージが出ていたということです。

    
            #// [CmdletBinding()]属性により「-Debug」が使えるようになる
            #// 内部的に$DebugPreference変数が設定される
            #// この時、Windows PowershellとPowerShell Coreで設定値が異なる!
            [CmdletBinding()] 
            param([String]$binPath, [Switch]$help)

            #// $ConfirmPreferenceは「None」
            #// Noneに設定していも、$DebugPreferenceが「Inuquire」なら
            #// Write-Debug時に確認メッセージが出る
            $ConfirmPreference = 'None'
            ...
            ...
            Write-Debug ("start $myName / $myVersion")
            ...
            ...
            Write-Debug ('$binPath = ' + $binPath)

    いや～、PowerShellは謎が多いし奥が深い（おもしろい）

  • 「$ErrorActionPreference」は、エラー時の挙動を決める設定

    その前にまず似ているもので「-ErrorAction」というオプションがあるが、これは$ErrorActionPreferenceとは別のもの（似ているけど）

    • $ErrorActionPreference環境設定変数

      この環境設定変数は、スクリプト全体に対するエラーの挙動を指定するもの。

    • -ErrorActionオプション

      このオプションは特定のコマンドレット毎のオプション設定。あるコマンドレットに「-ErrorAction」が指定されていて、さらにスクリプトにも$ErrorActionPreferenceも設定されている場合、個別のコマンドレットについている方が強い 

      
                # スクリプトHoge.ps1
                $ErrorActionPreference = "Stop"   # Hoge.ps1スクリプト全体に対する設定
                ...
                Get-Item "C:\存在しなないフォルダ" -ErrorAction SilentlyContinue

                # 結果
                この例では、スクリプト全体に対してエラーがあった場合「Stop」が指定されているが、Get-Itemであるフォルダのデータを
                取ろうとした時に存在しなかった場合は「SilentlyContinue」で継続される（個別で設定した方が強いから）
      $ErrorActionferenceの主な設定値
      設定値 値の意味
      Continue (デフォルト) エラー メッセージが表示されるが止まらずに処理が継続される
      Stop 例外扱いになりスクリプトが停止（catch可能）する
      SilentlyContinue エラーを表示せずに続行。存在するかテストする時などに使う
      Ignore エラーを無視して続行（SilentlyContinueよりも強く無視、ログも残さない）
      Inquire エラー発生時にユーザーへ確認（Y/N）
  • 「$VerbosePreference」は、詳細表示を行うかどうかを決める設定

    Write-Hostだと表示のOn/Offを切り替えようと思うと、if文でOn/Offしないといけないが、Write-Verboseはこの$VerbosePreferenceで制御できる。またVerboseは[CmdletBinding()]で高度化しているので引数を定義しなくてもすぐ使える

    -Debugと一緒で[CmdletBinding()]しておけば、xxPreference変数に値を設定しなくてもいい（したらだめ）。引数に「-Verbose」を指定すると、Write-Verbose()の表示が行われるようになる。 

    
            My-Hoge.ps1
            [CmdletBinding()]     #// これで My-Hoge.ps1は高度化される
            param(
              [Switch]$Ver,
              [Switch]$help
            )
            ...
            #// [CmdletBinding()]をしておけば、以下のif文は不要!!
            # if ($verbose) {
            #   # Write-Verboseが表示される
            #   $VerbosePreference = 'Continue'
            # } else {
            #   $VerbosePreference = 'SilentlyContinue'
            # }
            ...
            Write-Verbose('$Neko = ' +  $Neko)    #// -Verboseが指定されていたら実行される
            Write-Verbose('$Usagi = ' + $Usagi)   #// -Verboseが指定されていなければ実行されない
